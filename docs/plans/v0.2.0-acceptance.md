# v0.2.0 acceptance evidence

The local acceptance suite covers the implementation matrix in the [implementation plan](v0.2.0.md). The machine-readable run counts are recorded in `validation/v0.2.0.json` and `evaluation/reports/pytest-py311.xml` / `pytest-py312.xml`. Deterministic vectors test cache policy; the separate pinned-model evaluations test embedding behavior and the declared synthetic workload.

The cross-backend acceptance fixture runs on memory, file-backed SQLite, and real Redis, with flat and HNSW indexes. Memory is intentionally process-local; reopening it creates an empty cache. Redis tests use unique owned generations. The legacy rollback test requires repository history, and CI now fetches that history explicitly.

## Changing-document RAG application evaluation

`examples/versioned_rag.py` retrieves an immutable document snapshot and uses its versions for lookup, generation and storage. `tests/test_versioned_rag_v2.py` checks changed answers, repeated hits, isolated tenants, scoped invalidation, and document changes while generation is in flight, across all six backend/index combinations.

Run `python -m evaluation.rag` with a real Redis service at `LONGCACHE_TEST_REDIS_URL`. This exercises the application workflow with the pinned BGE model. Results are recorded in `evaluation/reports/versioned_rag.json`. The authored document fixtures use an extractive generator. They demonstrate executable application integration and freshness, but do not measure a live LLM's answer quality or constitute customer dataset review.

## External release gates

Hosted CI requires the user's manual push. Domain representativeness and labels require review against actual application queries/documents. Release-candidate feedback requires a distributed candidate and a feedback window. These gates remain pending until that evidence exists; passing local tests cannot establish them.
