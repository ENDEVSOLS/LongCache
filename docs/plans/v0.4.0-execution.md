# v0.4 execution record

**Branch:** `feat/v0.4-deployment-readiness`.
**Baseline:** `e384615` (development v0.3.0 package).
**Status:** implementation in progress. No push, tag, publication, or v0.4 release qualification is recorded here.

The first implementation slice adds an opt-in shared Redis keyspace, guarded mutations, revision/journal awareness for local FAISS indexes, Redis-checked replay, and exact-request leases across processes. The default single-process behavior remains selected by configuration.

The initial local validation on Python 3.12 used a disposable Redis 7.4.11 container bound to localhost, with persistence disabled. At that stage, `tests/test_shared_redis_v4.py` passed 11 tests, including the two-process 20-request origin-count check. The full suite passed **463 tests, four model-download tests skipped** with the real Redis service available. Ruff lint passed. These runs precede later lease-failure, restart, and integrity tests and must be refreshed against the final artifact. The service was then replaced with a pinned Redis 7.2 container for the target-version run; its results are recorded separately below.

On **Redis 7.2.17**, Python 3.12.14, and the existing offline pinned model snapshot, the complete suite passed **474 tests with zero skips**. It includes process-crash lease takeover, a trimmed-journal rebuild, restarted HNSW, strict/bypass coordination faults, manifest incompatibility, and invalidation racing a new store. Ruff lint/format, strict MkDocs, and the runnable two-instance RAG example passed. The RAG example uses authored documents and a deterministic fixture embedder; it is integration evidence, not a live-provider quality measurement. The Redis 7.2.17 test container had snapshot/AOF persistence disabled and was bound to localhost.

The frozen pinned-model v0.3 safety evaluation passed unchanged on the current checkout: 4,800 requests, 2,000 accepted hits, zero incorrect hits, zero isolation errors, full declared safe-paraphrase coverage, and full unsupported-case bypass. Its cases are synthetic and correlated; this is a regression check for the existing single-process path, not a shared-deployment quality estimate.

The first 10,000-entry benchmark run exposed a quadratic shared-store cost: a Python count scanned the entire partition after every store even though the Redis mutation already enforced capacity. Removing that redundant scan reduced the 1,000-entry smoke run from several minutes to about seven seconds. A later run exposed a shared lookup that rebuilt a large local index after invalidation and could exceed the five-second synchronization deadline. The shared store now returns its commit revision, so a process advances its own cursor only across contiguous local commits. Remote deletion and invalidation events advance the cursor while authoritative Redis replay guards reject stale vectors; a background sweep compacts those vectors. Regression tests cover a remote write between local commits and invalidation replay without a full synchronous rebuild.

The configured local deployment benchmark compares archived `e384615` v0.3 source, the current single-process path, and two shared processes against the same Redis 7.2.17 service. It measures Flat and HNSW at 1,000 and 10,000 entries, five repeats per case, 2,000 warm reads per repeat, and a 20-request origin burst. Each case has 10,000 samples for p99. It records throughput, peak worker RSS, cross-process visibility, and source/config hashes. The hash-matched local run passed the configured latency, origin-count, and one-second visibility gates. Its slowest observed shared write visibility was 15.9 ms and invalidation visibility 3.5 ms; every shared burst made one origin call. The candidate source hash was `0b0a283f7710091d25a6a00a60309e9aef14ef278f80739604c7ce4a027aca8f`. These are same-host synthetic fixture measurements on an uncontrolled development machine, not sustained production-load or hosted-CI evidence. The ignored raw report is `evaluation/reports/v0_4_deployment.json`; repeat it with:

```bash
mkdir -p /tmp/longcache-v03-baseline
git archive e384615 | tar -x -C /tmp/longcache-v03-baseline
LONGCACHE_TEST_REDIS_URL=redis://localhost:16379/0 python -m evaluation.deployment --baseline-root /tmp/longcache-v03-baseline --release --reference-host-id local-redis-7.2-development
```

The next implementation slice replaced large-ID invalidation scripts with a revision-checked live count and an atomic watermark/epoch update; physical cleanup uses batches of at most 256 IDs. It also capped active distributed leases at 1,024 by default, using a Redis-owned expiry registry and monotonic fencing counter. The full suite after these changes passed **481 tests with zero skips** on Python 3.12.14, Redis 7.2.17, and the existing offline pinned model. New cases cover 600-entry invalidation and paged cleanup, lease capacity/expiry, long-running sync-origin renewal with an async follower, async cancellation, and client reconnect after a remote invalidation. These tests do not establish server failover or a controlled write-churn envelope.

A wheel and source distribution were built from this later development checkout. The wheel installed into clean Python **3.11.16 and 3.12.14** environments with CPU-only Torch and its Redis extra. The existing installed-wheel sync/async/SQLite smoke and a shared Redis write/read/invalidation/refill script passed on both versions. The build CI job now runs these scripts against a Redis service, but hosted CI has not run on this unpushed branch. The plain PyPI dependency resolution selected multi-gigabyte CUDA packages, so the clean environments used the CPU-only Torch path already used by CI. The Python 3.12 installed environment occupied about 1.2 GB; this is an environment measurement, not a package-size comparison or a lighter-embedding decision. A non-escalated local process check could not wake an asyncio thread future because this sandbox blocks its stream file descriptor; the same installed-wheel smoke passed under normal local process permissions.

The source plan was copied into this repository as [v0.4.0.md](v0.4.0.md). The original workspace plan remains outside this package. The benchmark above was measured before the later invalidation/lease changes, so its candidate hash does **not** describe the current checkout. Current evidence covers local functionality and repeatable development-host benchmarks, not v0.4 release qualification. Sustained write/delete churn, upper bounds for every shared metadata class, server outage/restore, operation receipts, real-model shared-mode evaluation, a controlled reference-host run, hosted CI, and the lighter embedding investigation remain open. The package metadata intentionally remains at v0.3.0 while those gates are open.
