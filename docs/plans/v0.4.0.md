# LongCache v0.4.0 Implementation Plan — Deployment Readiness

**Status:** implementation in progress; this plan is not evidence of v0.4 release qualification.
**Prepared:** November 2, 2026.
**Implementation target:** this repository, whose baseline package metadata declares v0.3.0 and Python >=3.11.
**Primary reference:** [public roadmap](https://github.com/ENDEVSOLS/LongCache/blob/main/ROADMAP.md).
**Previous plan:** [v0.3.0 reliability](v0.3.0.md).
**Capacity:** one to two developers; provisionally 10–16 weeks, including qualification. This is an effort allowance, not a release date.

All source paths below are relative to this repository root unless stated otherwise. New names, defaults, limits, and budgets are proposals to freeze in milestone A. Source inspection informs this plan; historical execution records are not fresh test results or proof of publication.

## 1. Outcome and release scope

Version 0.4.0 adds one explicitly supported deployment in which multiple application processes share a Redis cache without silently diverging local search indexes or republishing invalidated results.

The main example is two workers answering the same scoped question. Worker A stores an answer; worker B discovers it without restarting. When A invalidates the relevant entries, B stops serving them. If A dies during generation, B can eventually recover, and A cannot later publish through an expired ownership lease.

| Required delivery | Completion condition |
| --- | --- |
| Opt-in Redis multi-instance mode | Defined visibility, expiry, deletion, invalidation, recovery, and capacity behavior pass independent-process tests. |
| Distributed exact-request coalescing | Healthy overlapping identical requests execute the origin once; lease loss prevents obsolete publication and followers have bounded waits. |
| Explicit RAG freshness across instances | Existing corpus/document versions and tag invalidation work with shared coordination, including updates during generation. |
| Embedding/dependency investigation | Reproducible install-size, startup, quality, and compatibility comparison; an explicit ship/defer decision. |
| Scale evidence | Repeatable latency, throughput, memory, convergence, and recovery measurements on the declared topology. |
| Upgrade and operations guidance | New shared generations, outage behavior, limits, deployment requirements, cleanup, and rollback are documented and tested. |

**Optional candidate:** controlled prewarming. Include it only after the required correctness work passes and a concrete user dataset/use case justifies the work. Its absence does not block v0.4.0.

**Deferred:** Redis Cluster/Sentinel/automatic failover support, replica reads, multi-region consistency, arbitrary Redis-compatible products, a separate cache server, Redis vector search, new databases, streaming replay, automatic retrieval-metadata discovery, adaptive thresholds, and general conversation caching. Existing single-process memory, SQLite, and Redis behavior remains supported.

## 3. Supported topology and consistency contract

### 3.1 First supported deployment

- Two or more independent LongCache processes connect to one writable Redis authority. Reads and writes use that authority, with finite connect/socket deadlines.
- Redis 7.2 is the initial compatibility target; pin exact CI images and record the measured server/client versions. Retain Python 3.11/3.12 until separately qualifying additional interpreters.
- Each process owns its embedder, FAISS index, local flight registry, and resource budgets. Redis owns authoritative entries, ordered mutations, invalidation state, and distributed leases.
- All participants use the same shared manifest, embedding fingerprint, identity/policy version, and shared coordination configuration. Incompatible participants fail initialization.
- Start with flat indexes as the reference implementation. Ship shared HNSW only after the same correctness/recovery suite and its useful-hit/recall evaluation pass; keep existing single-process HNSW support either way.
- Use a dedicated/non-evicting Redis allocation with capacity headroom. Arbitrary eviction of coordination keys, direct mutation of owned keys, restoring old data into a live generation, and non-LongCache writers are outside the contract.

### 3.2 Observable guarantees

| Event | Required behavior |
| --- | --- |
| Acknowledged write on A, then lookup starts on B | B catches up through the acknowledged mutation before deciding hit/miss, or raises/bypasses explicitly. It does not silently search an older index. |
| Acknowledged deletion/invalidation, then lookup starts | The deleted/invalidated answer cannot be accepted. An index vector may remain temporarily, but authoritative validation rejects it. |
| TTL expires | Redis time/remaining TTL determines shared validity; local clock skew cannot extend an entry's cache eligibility. |
| Mutation overlaps lookup | A hit is authorized at a final atomic Redis validation point. If invalidation follows that point, the operations overlap; LongCache cannot retract a response already authorized. |
| Generation overlaps invalidation | Work captures a shared publication fence before generation. Invalidation prevents that older work from storing or sharing afterward. The original caller may receive its own origin response under the documented v0.3 behavior. |
| Missed wakeup/disconnected process | Durable state determines catch-up; notifications are unnecessary for correctness. |
| Process restart | Rebuild from a validated snapshot and journal before cached replay; no trusted process-local cursor survives by assumption. |
| Redis unavailable | `raise` stops cache-dependent work; `bypass` may run the origin without distributed deduplication and never serves an unverified local answer. Maintenance errors remain visible. |
| Lost lease/process pause | A new owner may eventually execute. The old owner cannot commit after ownership expires or changes. Exactly-once provider execution is not promised. |

The consistency promise concerns cache reuse and publication under one unchanged Redis authority. It does not establish the truth of source documents or make remote provider calls transactional.

Application-process restarts and transient connection recovery are automatic recovery cases. Redis-server restart, failover, or data rollback invalidates the deployment's coordination assumptions: stop shared traffic, rotate the shared generation, and restart participants before resuming. Do not advertise transparent server-restart/failover recovery in v0.4. A future extension needs an independently tested server-incarnation/fencing protocol.

## 4. Architecture: durable mutations with local search

Choose **authoritative Redis storage plus an ordered mutation journal and replaceable local FAISS indexes**. Keep coordination in a deep module with a small interface; decorators and provider adapters continue to use the existing execution module.

Redis Pub/Sub provides at-most-once delivery, so it cannot be the recovery record. Initial v0.4 should use bounded journal polling rather than add a separate Pub/Sub lifecycle. This choice follows the [Redis Pub/Sub delivery contract](https://redis.io/docs/latest/develop/pubsub/). If wakeups are added later, the journal remains authoritative.

Redis Streams can retain ordered events and support range reads; each process needs to observe every relevant mutation, so do not use one consumer group to divide index updates among workers. See [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/).

### 4.1 Module responsibilities

| Module | Responsibility and interface |
| --- | --- |
| New `core/coherence.py` | Own synchronization state, cursor, snapshot installation, invalidation fences, and bounded recovery. Internal operations: `synchronize(deadline)`, `capture_fence(...)`, `validate_replay(...)`, and `commit(...)`. |
| New `backends/redis_shared.py` | Redis adapter implementing the shared protocol, manifest checks, journal pages, guarded reads/writes, invalidation, and bounded maintenance. Reuse serialization where safe without changing legacy Redis behavior. |
| New `backends/redis_scripts/` | Small versioned Lua scripts for atomic validation/mutation/election. Package these resources in wheel and sdist. |
| New `core/distributed_singleflight.py` | Lease acquisition/renewal, remote waiting, terminal receipts, takeover limits, and stale-owner rejection behind the execution seam. |
| Existing `core/execution.py` | Select local or shared coordination and preserve one prepare/lookup/compute/admit/store/return flow. No provider-specific lock implementations. |
| Existing `core/index.py` | Idempotent add/remove by entry ID, atomic replacement, vector validation, and compaction honoring flat/HNSW configuration. |
| Existing `core/cache.py` | Delegate shared-mode operations; retain the public lookup, storage, execution, maintenance, and lifecycle interface. |
| Existing identity/policy/embedding modules | Remain the single implementations of scope, exact identity, admission, verification, codecs, and vector compatibility. |
| Existing lifecycle/observability modules | Own all new work and fixed-schema health/metrics. |

Use the legacy local path and Redis shared adapter as the actual variations at the seam. Do not require memory/SQLite to pretend they implement distributed leases or journal semantics.

### 4.2 Proposed configuration

```python
# Proposed v0.4 configuration; unavailable until implementation.
config = CacheConfig(
    backend="redis",
    deployment_mode="shared",  # default remains "single_process"
    redis_url="redis://localhost:6379/0",
    cache_id="support",
    generation="v04-shared-1",  # fresh, explicitly chosen generation
    cache_error_policy="raise",
    distributed_singleflight_enabled=True,
)

with LongCache(config, embedder=embedder) as cache:
    answer = cache.get_or_compute(
        question,
        lambda: generate_from_snapshot(snapshot),
        context=context_from_snapshot(snapshot),
        tags=("document:returns-policy",),
    )
```

Proposed shared settings: synchronization deadline 5 seconds; journal page size 256; journal retention 100,000 events; lease duration 15 seconds; renewal interval 5 seconds; follower wait continues to use the existing 30-second setting; polling uses bounded 25–250 ms jitter. Freeze exact settings after the baseline, before tuning.

Validation must reject shared mode on unsupported backends, nonpositive/unbounded limits, renewal intervals too close to lease expiry, inconsistent distributed/local singleflight flags, and manifest-incompatible coordination settings. `CacheConfig.from_dict/from_env` must support the new fields and still reject unknown safety settings.

Initial capacity targets: 10,000 live entries per partition, 50,000 per shared generation, at most 1,024 local active flights, and 1,024 active distributed leases per generation. Add explicit bounds for distinct partitions, tags/tombstones, control receipts, retained journal bytes, snapshot bytes, and per-entry metadata before interface freeze. Requests exceeding a bound receive a typed capacity result; cleanup/rebuild must not allocate an unbounded list.

These are proposed qualification limits, not measured performance claims. Do not publish them as supported until benchmark and fault evidence pass.

Keep errors specific and redacted: a synchronization deadline/gap is a cache operation failure with a bounded synchronization stage; incompatible manifests/configuration fail initialization and are never suppressed by bypass; expired/superseded ownership is a coordination failure, not a provider failure. Add public error subclasses only where applications need a distinct recovery action. Remote provider failures use the existing leader-error family with a sanitized reason, without claiming to reconstruct the original Python exception.

## 5. Shared storage and atomic mutation protocol

### 5.1 Versioned ownership

Use a separate proposed prefix, `longcache:shared-v1:<cache_id>:<generation>`. Preserve the existing `longcache:v2:...` single-process keyspace. The shared protocol version and request-identity format are separate concepts: retain identity format 2 where its meaning is unchanged.

The immutable shared manifest binds storage protocol, cache ID/generation, embedding descriptor, policy/sharing configuration, coordination protocol, and limits whose mismatch would affect shared behavior. Include a random generation incarnation in every lease/fence/receipt. Missing metadata in a nonempty keyspace is an error, never implicit initialization.

Owned data includes:

- Global monotonic mutation sequence and ordered Stream events, with event IDs derived from sequence numbers.
- Immutable entry IDs and payload digests; entries record canonical identity, embedding fingerprint, commit sequence, shared expiry, and bounded tags.
- Namespace/partition membership, tag references, and creation-order metadata for deterministic capacity enforcement.
- Generation-clear, partition, and tag invalidation watermarks, plus a generation-wide publication epoch.
- Leases, monotonic fencing counter, bounded terminal receipts, and operation-id receipts.
- A generation integrity marker used to quarantine uncertain partial mutations.

Never place raw prompts, answers, tenant/user IDs, instructions, credentials, or full identity records in journal events or lock names. Events contain operation type, opaque entry/partition/tag references, sequence, and epoch. Hashes are pseudonymous references, not an anonymity guarantee; Redis remains trusted application storage.

### 5.2 Atomic operations

Implement guarded mutations with bounded Lua scripts. Scripts execute atomically relative to other Redis commands and block the server while executing, so avoid scans and unbounded loops inside them. See [Redis programmability](https://redis.io/docs/latest/develop/programmability/).

For an admitted write:

1. Serialize, size-check, admit, and embed outside Redis and outside global locks.
2. Provide an operation ID, expected manifest/incarnation, publication epoch, partition identity, optional lease owner/token, expiry policy, payload/vector, and bounded tags.
3. Check manifest/integrity and look for an existing receipt matching this operation ID and immutable arguments. A matching receipt resolves the historical mutation outcome even if the lease later expired; it does not authorize current replay. For a new mutation, check expected epoch, lease ownership/unexpired TTL when applicable, and capacity before changing state.
4. Set the integrity marker, reserve a sequence, write the entry and bounded references, perform any bounded eviction, append its journal event, and record the operation receipt.
5. Clear the integrity marker only after the entire protocol succeeds. Return entry ID, commit sequence, and server-derived expiry.

Choose immutable entry replacement rather than in-place response mutation. Retries of the same operation ID return the same recorded outcome; never blindly repeat an ambiguous successful write. Receipt retention and retry deadlines must be aligned; after the receipt window, report an indeterminate outcome rather than pretending replay is safe.

Redis atomic execution does not provide transaction rollback for runtime errors; [Redis transactions](https://redis.io/docs/latest/develop/using-commands/transactions/) explicitly document that limitation. Validate key types/arguments before writes, maintain `noeviction` capacity headroom, and leave the integrity marker set if a later script step fails. Every shared read/write/lease guard refuses a marked generation. Recover with an explicit repair procedure or a new generation; never trust a possibly incomplete journal.

### 5.3 Invalidation, deletion, and expiry

- A partition invalidation atomically advances its invalidation watermark, the publication epoch, and the journal. Any entry committed at or before that watermark is ineligible.
- Tag invalidation does the same for the exact `(partition, tag)` and must fence older writers even when no entry currently exists. Keep the existing exact-context semantics.
- Initially advance the **generation-wide publication epoch on every explicit invalidation**, conservatively fencing unrelated in-flight writes as v0.3 does locally. Narrower fences can follow measured need; do not add unbounded per-source coordination first.
- Large logical invalidations take effect immediately through watermarks. Reclaim old hashes/vectors/references in bounded batches afterward; do not delete an entire generation in one Lua loop.
- Keep invalidation watermarks until generation retirement or a proven safe compaction point. TTL-expiring a tombstone must never make an old entry valid again. Bound their cardinality and reject excess metadata instead of unsafe pruning.
- Individual deletion is idempotent and journaled. Operator clearing uses the same logical fence and owned-prefix cleanup; never `FLUSHDB` or `FLUSHALL`.
- Use Redis time and millisecond TTL for shared expiry, with explicit `ttl=0` meaning no expiry. Check expiry at final replay as well as candidate load.
- Natural TTL expiration need not append a journal event: candidates must be reread from authoritative storage. Periodic bounded cleanup removes expired membership references and local vectors.
- Persisted hit increments use an existence/validity guard so expired/deleted hashes cannot be recreated by `HINCRBY`.
- Shared `max_entries` enforcement is atomic, excludes invalidated/expired entries, and produces deletion events for evictions. Conservative capacity rejection while cleanup catches up is acceptable; silent overcommit is not.

Existing invalidation returns a count; preserve a documented count of live entries invalidated at its serialization point. For large tag sets, compute a candidate count in pages and validate the revision before the atomic watermark update, retrying within a deadline. Do not return a physical cleanup count as if it were the logical invalidation count. If this cannot meet boundedness budgets, freeze an explicit additive maintenance-result interface in milestone A and document compatibility before implementation.

## 6. Index synchronization and recovery

### 6.1 State machine

`UNINITIALIZED → REBUILDING → READY → CATCHING_UP → READY`

Recognized connectivity failures move to `DEGRADED`; manifest/integrity/vector corruption moves to `QUARANTINED`; shutdown moves to `CLOSING → CLOSED`. Only a synchronized `READY` state may authorize cached replay. Expose bounded state/reason diagnostics through existing operator metrics.

### 6.2 Bootstrap and journal catch-up

1. Read/validate manifest, integrity, epoch, and sequence `s0` from Redis.
2. Enumerate a generation-owned entry-ID registry with bounded pages; load live valid entries and deduplicate by immutable ID. Build a replacement index off to the side. Do not delete/recreate that registry or reuse entry IDs within a live generation.
3. Read target sequence `s1` after enumeration and verify unchanged manifest/incarnation/integrity. Replay every journal event from `s0 + 1` through `s1` into the replacement, fetching immutable additions and applying deletion/invalidation events idempotently. Never advance a snapshot cursor past an unapplied event.
4. Reconcile entries against current partition/tag watermarks, vector/identity contracts, and authoritative existence/expiry. Keep entries logically invalidated after the target out of replay even if their vectors await compaction.
5. Verify the required journal range was retained and continuous. Atomically install the replacement index and cursor `s1` together. Discard partial replacements on cancellation/failure; catch up subsequent events before the next lookup's decision.
6. For normal catch-up, read the current authoritative target sequence and apply journal pages from the local cursor through that target. Every expected sequence must be present; additions/removals must be idempotent.
7. For a trimmed/gapped journal, wrong incarnation, impossible sequence regression, or lost local state, discard trust and rebuild within a bounded retry/deadline. Do not skip a gap because newer events are available.

The proof relies on immutable IDs: an eligible entry present throughout the registry scan is enumerated; an entry introduced during the scan is covered by the journal; removals/invalidations cannot resurrect an ID. Redis scanning can return duplicates and does not produce a snapshot, so deduplication and journal replay are required. Freeze and test these assumptions against the [Redis SCAN guarantees](https://redis.io/docs/latest/commands/scan/), including registry encoding changes and concurrent cleanup. `COUNT` is a work hint rather than a strict response-size bound; enforce separate application byte/entry limits.

If the journal trims history faster than bootstrap can consume it, fail/bypass at the synchronization deadline instead of accepting an incomplete index. Qualify retention against measured mutation rates and worst-case rebuild time. A quiescent revision-checked rebuild is an acceptable diagnostic fallback, but normal startup must not require traffic to stop.

Each process reads its own event range. A shared consumer group that hands different events to different processes would leave every local index incomplete.

### 6.3 Lookup and hit authorization

1. Validate trusted identity and initialize the embedding contract as today.
2. Synchronize the index through the target sequence read when lookup begins.
3. Search the appropriate partition, reread candidate entries, and run existing integrity, codec, admission, and verification checks.
4. Invoke a final atomic Redis guard with entry ID, expected immutable payload/metadata identity, invalidation state, manifest/incarnation, and current epoch. Check entry TTL using server time. Compare the exact bounded encoded payload/immutable metadata that was verified, or an equivalent proven immutable-content token; comparing a writable stored digest field alone is insufficient.
5. Return the verified decoded payload only if the guard succeeds. A changed/deleted/invalidated candidate can trigger a bounded recheck or safe miss; repeated churn becomes an explicit synchronization failure/bypass.

All hit paths must cross this guard: direct lookup, `get`, `get_or_compute`, local followers, remote followers, inspection where relevant, and supported integrations. An in-memory completed response must never bypass shared invalidation/TTL checks.

Do not carry legacy client-wall-clock expiry comparisons into shared replay. Convert server-returned remaining lifetime to a conservative local monotonic deadline where needed for waiting, and still perform the final Redis guard. Add tests with opposite client clock skew on the two workers.

Snapshot/catch-up jobs and index replacement belong to the existing tracked lifecycle. Do not hold the index lock during provider execution, application hooks, sleep, or lease waits. Keep a documented lock order and coalesce concurrent local synchronization attempts into one job.

### 6.4 Connection and mutation failures

- On a transient disconnect, mark synchronization uncertain, discard pending local mutations, reconnect with backoff, validate metadata, and rebuild/catch up before replay.
- On a failed local index update after a successful Redis commit, rebuild locally. Do not delete the successful shared entry as compensation for one process's FAISS error.
- On a lost mutation response, resolve the operation receipt; never execute the provider again just to determine whether storage succeeded.
- On an uncertain generation, `bypass` invokes origin-only work; it cannot use stale local entries or distribute that result without a valid fence.
- Distinguish transient connection failures from server restart/data rollback. The latter requires the generation rotation procedure in section 3.

## 7. Distributed singleflight after coherence

### 7.1 Identity and guarantees

Retain local singleflight as the first layer, so one representative per process performs distributed coordination. The distributed flight identity uses the existing exact request key, effective TTL, normalized tags, shared generation incarnation, policy identity, and captured publication epoch.

Identical text in different tenants/users/models/instructions/source versions/codecs must not join. Semantically similar questions never share a flight merely because their vectors are close.

Supported entry points remain `get_or_compute`, `aget_or_compute`, query-only decorators, and the supported OpenAI adapter. Separate manual lookup → compute → set calls and arbitrary ASGI invocations cannot promise distributed coalescing or fence a computation interval LongCache does not own.

### 7.2 Lease protocol

1. Prepare identity and perform a synchronized cache lookup.
2. Atomically acquire a missing lease with a unique owner ID, monotonic fencing token, finite Redis TTL, and captured epoch; enforce the global active-lease bound.
3. Recheck the cache after acquisition before calling the origin.
4. While the origin runs, renew only through compare-owner/token/epoch scripts. Use a tracked, bounded renewal task that cannot be starved by a long provider call occupying the ordinary cache worker pool.
5. Admit/validate the result. Publish the entry and successful terminal receipt through the same fenced mutation protocol, validating lease ownership and TTL at the commit point.
6. Release only the lease still owned by this owner/token. Delayed release cannot remove a replacement owner's lease.

Owner-qualified release and explicit fencing follow the failure considerations in [Redis distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/). This plan uses a single-authority contract, not Redlock or an automatic-failover guarantee.

Use Python's exact integers for token comparisons/serialization; do not compare long-lived 64-bit counters through lossy Lua floating-point conversions. Define overflow/rotation behavior and test tokens beyond `2**53` before freezing the script protocol.

### 7.3 Followers and failures

Remote followers poll bounded lease/receipt state with jitter, stop at their own deadline, and reuse only an admitted stored entry through the normal final guard. Store terminal control state with bounded retention; do not serialize provider exceptions or arbitrary Python objects into Redis.

| Case | Required result |
| --- | --- |
| Healthy owner, admissible result | One origin invocation across the overlapping request burst; followers validate and decode separate response objects. |
| Follower timeout/cancellation | Release only that waiter's local resources; never delete the remote owner's lease. |
| Owner provider error | Owner receives original error; remote followers receive a sanitized typed leader failure. No provider auto-retry. |
| Owner cancellation | Best-effort terminal failure and qualified release; if owner vanishes, lease expiry enables recovery. |
| Rejected/refused/oversized response | No cached/shared payload. Preserve documented non-shareable fallback semantics: followers may execute their own callbacks; that path has no one-call promise. |
| Owner dies, lease expires | A waiting representative may make at most one bounded takeover attempt before its original deadline. The next owner uses a new token and rechecks the cache. |
| Owner pauses past expiry, then resumes | Provider execution may overlap a replacement owner's work; the expired owner cannot renew, publish, or delete the new lease. |
| Lease renewal uncertain | Mark ownership lost conservatively. Never infer validity from a local timer or publish during Redis outage. |
| Invalidation during generation | Incremented shared epoch rejects the owner's commit and terminates old followers with invalidation. |
| Cache write fails after successful generation | Return or raise under existing cache error policy; do not rerun origin. Remote followers do not receive unpersisted transient payloads. |

Successful receipts refer to an immutable stored entry, expected identity, digest, epoch, and expiry. A receipt outliving its entry is not permission to serve it. Bound terminal-state retention, active-lease accounting, poll tasks, renewers, and waiter counts. Expired active-lease references must be cleaned before rejecting global capacity.

Callbacks must be safely repeatable: distributed coalescing reduces duplicate execution but cannot promise exactly-once external effects under crashes/lease expiry. Document this next to the execution methods and examples.

## 8. RAG freshness: extend existing mechanisms

### 8.1 Required workflow

1. Resolve tenant/user from trusted authentication.
2. Retrieve an immutable document snapshot with its document IDs/revisions and corpus version.
3. Put those exact versions into the existing `RequestContext`. Every answer-affecting source must participate; document ordering belongs in identity where it changes generation.
4. Call `get_or_compute/aget_or_compute` with a callback bound to that same snapshot and bounded explicit document tags.
5. After source updates, new retrievals produce new versioned contexts. Never relabel an answer generated from old documents with a newly read current revision.
6. Use exact-context tag invalidation to revoke entries in a known context. In shared mode it also fences older in-flight publication across processes.

Add a multi-process runnable example and extend `evaluation/rag.py` or add `evaluation/deployment.py` to exercise it. Keep fixture/extractive generation clearly identified; add a pinned real-embedding run without claiming live-LLM factual accuracy.

### 8.2 Precise limits

- Existing `invalidate_by_tag(tag, context=...)` affects that context's partition. It does not suddenly become a cross-tenant or all-document-revisions operation.
- A changed corpus/document version creates a new partition. Old entries may remain physically until expiry/cleanup, but cannot satisfy the new context.
- A caller deliberately supplying an old snapshot can still ask an old-version question. LongCache does not discover the source system's current revision. If the application requires revoking old snapshots, it must stop accepting them and invalidate the known affected contexts.
- Do not silently broaden `invalidate_by_tag` to solve global source revocation. A future cross-context source registry requires a separate permission/scope contract and concrete demand.
- Global invalidation is not inferred from semantic similarity. Retrieval metadata automation remains deferred until the explicit workflow passes.

Required scenarios: document change, deletion/tombstone from the retriever, corpus replacement, changed retrieval set, empty retrieval, tenant isolation, document-ID reuse in another tenant, multi-document partial updates, invalidation while generation is paused, old-version generation finishing after a new-version request, and restart/reconnect on either worker.

## 9. Embedding size, startup, and dependency investigation

The required deliverable is a measured decision, not a promise to ship ONNX. Preserve the current model option unless compatibility and migration are documented.

### 9.1 Compare three bounded options

| Option | Question |
| --- | --- |
| Current sentence-transformers/PyTorch CPU path | What do a clean installation, model download, import, first embed, steady-state embed, and RSS actually cost? |
| sentence-transformers ONNX backend | Does execution/startup improve, and which Torch/transitive dependencies remain installed? |
| One direct ONNX Runtime adapter behind `BaseEmbedder` | Can an optional extra materially reduce installation size while reproducing required tokenization, truncation, pooling, and normalization? |

Sentence-transformers documents ONNX support but warns that exporting the transformer alone does not include sentence pooling/normalization. A direct adapter must implement and test those model-specific semantics. See [Sentence Transformers efficiency documentation](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html).

Measure clean environments from the built artifact, with exact dependency/model/artifact revisions. Separate network download time from local cold start and warm-cache start. Record compressed download bytes, installed site-packages bytes, model bytes, import time, first embedding time, warm latency, throughput, and peak RSS.

### 9.2 Compatibility and ship criteria

- Run frozen quality gates and near-threshold cases; measure similarity/ranking agreement and useful-hit coverage, not just vector dimension or average cosine agreement.
- Treat a new runtime/tokenizer/export/quantization implementation as a new embedding fingerprint and require a new cache generation by default. No cross-runtime persisted vector mixing without explicit equivalence evidence.
- Extend descriptor metadata with runtime/artifact identity where needed. Do not mutate existing descriptor meanings silently or accidentally invalidate all legacy descriptors.
- Package the alternative as optional initially. Keep existing `pip install longcache` behavior for v0.4 unless a separately reviewed migration warrants changing default dependencies.
- A truly lighter extra cannot remove unconditional Torch dependencies by declaration alone. Inspect wheel metadata and a clean resolved environment; if a core/extras split is required, either design it with migration notes and tests or defer the smaller-install claim.
- Proposed admission target: at least 25% lower clean installed dependency bytes or 20% faster local first-embedding startup, with frozen safety/coverage gates passing and no unexplained regression. Freeze the target before measurement; publish negative findings if it fails.
- Revisit NumPy <2 through exact Python/NumPy/FAISS/Torch/runtime compatibility cells and clean wheel installs. Never widen the range based on version age or an assumption about ABI compatibility. Keep the pin if the matrix is incomplete.

Platform support is only the tested wheel/runtime matrix. GPU acceleration, quantization, different default models, and ARM/macOS claims do not enter scope automatically.

## 10. Optional controlled prewarming

Do this after shared consistency, lease fencing, and freshness gates pass. Allocate an additional one to two developer-weeks or re-estimate scope; do not consume the required qualification window.

Proposed interface: a Python `prewarm(rows, *, dry_run=True, limit=...)` operation before adding a CLI. Use bounded JSONL input through an application-owned loader. Never import arbitrary logs, pickle objects, or automatically crawl documentation.

Every row supplies a query, approved response, trusted explicit scope/context, source versions, TTL, tags, and a stable import row ID. Use the same identity, codec, admission, capture-size, embedding, capacity, mutation, and invalidation protocol as live traffic. Missing identity is rejected; it is not replaced with a shared default.

Dry run returns accepted/rejected/duplicate counts and bounded reason codes, with zero cache mutation or model download unless explicitly required by the documented validation mode. Define whether "accepted" means structural eligibility or full embedded/admission eligibility. Use the same policy for import and dry run; state which later runtime failures remain possible.

Bound rows, bytes, tags, provider-independent work, and per-batch runtime. No provider calls. Make repeated row IDs idempotent, define duplicate query/context handling, and checkpoint only completed rows. On cancellation, completed rows remain individually valid; the batch is not falsely reported as atomic.

Candidate gates: scope isolation, source-version mismatch, invalid/oversized rows, invalid JSON/codec, duplicate/repeated imports, expiry, restart/resume, partial failure, admission rejection, invalidation during import, and removal under the same tag/version rules as live entries.

## 11. Acceptance tests and fault harness

Use tests through public `LongCache` methods and the internal coherence interface for deterministic protocol faults. Independent OS processes and a real Redis server are required for distributed claims; two objects in one interpreter are insufficient evidence.

Create `tests/shared/` with spawned-process workers, IPC barriers, deterministic embedding fixtures stable across process hash seeds, explicit per-test generations, bounded waits, and watchdog cleanup. Use a shared origin counter outside the candidate process so a crash cannot erase the evidence. Own only test-prefixed keys; do not flush a database.

| Test group | Required acceptance |
| --- | --- |
| Visibility | B initialized before A's write finds the new entry; acknowledged deletes, replacements, invalidations, and evictions are observed without restart. |
| Search | Correct partition selection, no closer cross-scope candidate leakage, expired candidates cannot hide eligible neighbors, duplicate journal replay does not duplicate vectors. |
| Replay races | Pause between verification/final guard and overlap deletion, TTL expiry, invalidation, epoch changes, and payload corruption. Exercise direct and follower paths. |
| Bootstrap | Writes/deletes during paginated scan, bounded retry exhaustion, cancelled rebuild, atomic install, malformed vector/manifest, empty and populated startup. |
| Journal | Duplicate events, missing/trimmed ranges, out-of-order application attempts, cursor regression, disconnected reader, and application-process restart. Every gap recovers or fails safely. |
| Mutations | Lost replies, same-operation retries, wrong key types, script runtime failure, memory/capacity errors, integrity-marker quarantine, and successful Redis commit followed by local FAISS failure. |
| Expiry/capacity | Redis-time expiry with skewed client clocks, no hit-counter resurrection, reference cleanup, concurrent max-entry enforcement, bounded invalidation/clear. |
| Coalescing | 20 healthy identical requests split across two processes cause one origin invocation; repeat sync, async, and mixed modes. |
| Lease faults | Kill owner, pause beyond TTL, delayed renewal/release, takeover race, token >2**53, lost commit reply, and renewal executor starvation. Old token never commits/releases new ownership. |
| Failure semantics | Provider exception, rejected response, follower timeout/cancel, owner cancel, outage before/after origin, strict/bypass, no hidden provider retry. |
| Freshness | All section 8 scenarios, including empty-store invalidation fencing a writer in another process. |
| Isolation | Tenant/user/sharing policy, namespace, provider/model/instructions, generation, TTL/tag flight policy, codec, corpus/document versions, and metadata-only maintenance authorization. |
| Lifecycle | Close during sync/rebuild/renewal/poll/compute, concurrent close, partial cleanup, cancellation churn, no connection closed while used, no task/thread/lease leak. |
| Compatibility | Existing single-process suite, unchanged legacy stores, new shared manifest rejection, separate generation upgrade and rollback, installed script resources. |
| Privacy | Logs, metrics, journal, lock names, and terminal failure records exclude sensitive payloads/raw identifiers; no unbounded metric labels. |

Tests asserting ordering use barriers, not arbitrary sleeps. Real lease/TTL tests use bounded polling with generous watchdogs and record scheduling delays. Repeated stress complements deterministic faults; random success is not a replacement for an asserted invariant.

Required distributed CI jobs fail when Redis/model prerequisites are missing instead of silently skipping. Optional platform/runtime jobs can be marked experimental, but cannot substantiate a support claim.

## 12. Benchmarks, metrics, and budgets

Add `evaluation/deployment.py` with `evaluation/configs/v0_4_deployment.json`, building on existing runner conventions. Preserve the frozen safety dataset/config and actual v0.3 source/artifact baseline. Do not substitute two labels running the same code for a before/after comparison.

### 12.1 Measurement matrix

- One, two, and four application processes against the same Redis authority; two is the minimum supported correctness topology.
- 1K/10K entries per generation, plus the proposed 50K qualification limit if feasible; several context partitions and both configured index types when claimed.
- Warm verified hits, distinct misses, healthy identical bursts, mixed reads/writes at declared rates, TTL churn, invalidation bursts, and overload.
- Separate deterministic embedding/protocol measurements from real pinned-model end-to-end measurements.
- Measure cold process startup/rebuild, incremental catch-up, lost-reader recovery, trimmed-journal rebuild, process crash takeover, and local index compaction.
- Record network placement/RTT, hardware/OS, Redis persistence/eviction settings, client pools, model, dimensions, threads, exact dependency versions, source/artifact/config/dataset digests, request mix, and process count.

Report p50/p95/p99, throughput, errors/timeouts/bypasses, origin invocations, useful-hit coverage, false hits, visibility/convergence delay, recovery duration, Redis CPU/memory, per-process RSS, journal bytes/lag, lease/poll traffic, and cleanup work. Include queue delay with scheduled-arrival workloads; do not hide overload by timing only completed successful requests.

Use at least 10,000 successful timing observations per claimed p99 cell, five alternating baseline/candidate repeats where comparable, raw sample retention, and variability. Short smoke runs must be labeled incomplete and must not emit a release-pass verdict.

### 12.2 Proposed budgets to freeze in milestone A

| Gate | Proposed target |
| --- | --- |
| Correctness/isolation | Zero known incorrect, cross-scope, expired, deleted, or invalidated accepted hits in the declared fault/safety suite. |
| Useful coverage | Preserve frozen safe-paraphrase and unsupported-shape gates; all-bypass behavior cannot pass. |
| Healthy distributed burst | Exactly one origin invocation for 20 overlapping identical admissible requests across two processes. |
| Stale ownership | Zero successful commits/releases by expired or superseded owners in deterministic faults and stress. |
| Post-ack visibility | A lookup beginning after acknowledgement catches up or explicitly errors/bypasses; never silently uses the older snapshot. |
| Healthy catch-up | At 10K entries, 2 processes, and the frozen same-host 95% read/5% mutation workload, p95 incremental catch-up <=250 ms. |
| Rebuild/recovery | At 10K entries, same-host deterministic-embedder setup, successful journal-gap/process-restart recovery <=5 seconds; measure 50K separately. |
| Legacy-mode regression | v0.4 single-process warm p95 <=1.15× actual v0.3 baseline +1 ms; p99 <=1.20× baseline +2 ms on the same host/cells. |
| Shared-mode overhead | Same-host two-process verified-hit p95 <= actual v0.4 single-process Redis p95 +5 ms; p99 +10 ms. Report network RTT separately. |
| Resource retention | Registry/task/connection/reference counts return to bounded steady state after churn; no growth proportional to completed requests. Freeze measured byte budgets for snapshots/journal/metadata. |

Numbers are planning targets, not existing results or portable SLAs. If baseline evidence makes a target unrealistic, revise it openly before implementation/tuning and record the reason. Never relax a failing gate after seeing final results to manufacture acceptance.

### 12.3 Operational visibility

Extend existing bounded metrics with synchronization state, journal lag/events, rebuild duration/count, shared final-validation failures, lease acquire/renew/lost outcomes, takeover count, follower wait/timeout, active local representatives, and cleanup backlog. Use fixed labels only. Keep diagnostic failures unable to change a valid cache decision.

Document readiness separately from liveness: origin-only bypass can keep an application alive while shared-cache readiness is degraded. Applications decide whether degraded caching should fail their own readiness check.

## 14. Upgrade, rollback, documentation, and packaging

### 14.1 Upgrade path

1. Verify current single-process behavior and retain the existing v2 generation.
2. Create a fresh `shared-v1` generation; do not relabel a populated v2 store or let v0.3 writers join it.
3. Deploy compatible v0.4 workers with identical shared manifest settings. Start with an empty shared cache; optional future import must obey normal admission and identity rules.
4. Confirm readiness/catch-up, run a two-worker canary including write/TTL/invalidation, and observe lease/resource health before expanding traffic.

## 16. Decision checkpoints and principal risks

| Risk | Decision rule |
| --- | --- |
| Journal and entry mutation diverge | Integrity-mark/quarantine on uncertainty; no local replay from an incomplete shared generation. |
| Bootstrap cannot finish under churn | Bound attempts, report degraded state, qualify a lower write envelope or redesign snapshot acquisition before claiming support. |
| Lease expiry permits duplicate provider calls | Document it, require repeatable callbacks, and reject stale publication; never advertise exactly-once generation. |
| Redis restart/failover reuses old ownership | Require coordinated generation rotation; no transparent failover claim in v0.4. |
| Tag/source scope becomes ambiguous | Preserve exact-context invalidation and application-managed versions; broader revocation requires a separate design. |
| Tombstone, receipt, membership, or journal growth | Enforce frozen cardinality/byte limits and bounded cleanup; generation rotation is the safe fallback. |
| New runtime changes similarity decisions | New embedding fingerprint/generation, frozen quality evaluation, retain existing runtime. |
| Claimed lighter install still pulls Torch | Inspect artifact dependencies and clean environments; publish the measured result or defer the claim. |
| Shared-mode costs exceed budgets | Measure RTT/script/poll/index costs, optimize behind the coordination seam, and rebaseline before release instead of weakening checks. |
| Required work exceeds capacity | Defer candidates and unsupported topologies; keep coherence, recovery, freshness, and fencing as release blockers. |

The recommended first release ships the shared Redis contract, guarded publication, explicit multi-instance RAG workflow, and measured evidence. Shipping a new embedding runtime or prewarming is contingent on its separate evidence; completing the investigation is required.
