# LongCache v0.3.0 Implementation Plan — Reliability

**Status:** implemented development specification; see the [execution record](v0.3.0-execution.md) and [acceptance evidence](v0.3.0-acceptance.md). The baseline inventory and proposed budgets preserve the planning context. Full controlled performance, hosted CI, and release feedback remain qualification gates.
**Prepared:** October 29, 2026.
**Implementation target:** `LongCache-fork/`, the workspace package declaring v0.2.0 and Python >=3.11.
**Primary reference:** [LongCache Roadmap, milestone 0.3](https://github.com/ENDEVSOLS/LongCache/blob/main/ROADMAP.md#03--reliability).
**Previous plan:** [v0.2.0 Safe Reuse](v0.2.0.md).
**Capacity assumption:** one to two developers; re-estimate after the baseline and interface review.

## 1. Outcome and scope

Version 0.3.0 makes supported cache use predictable when requests arrive together, dependencies fail, callers cancel, or the application shuts down. It preserves the v0.2 identity, admission, verification, persistence, and privacy rules.

The main user-visible example is an initially empty cache receiving 20 identical, eligible requests at once: one provider/function execution supplies the answer, rather than 20 executions. Different query texts or execution contexts never join the same flight. Different users may share only where the existing explicit sharing policy permits it.

| Required in v0.3.0 | Deferred from this implementation |
| --- | --- |
| Synchronous and asynchronous singleflight | Prometheus exporters and dashboards |
| Defined timeouts, cancellation, failures, retries, and capacity behavior | OpenTelemetry integration |
| Explicit cache failure policy | New JSON-schema/Pydantic response caching |
| Safe lifecycle across threads, clients, connections, and active work | Distributed singleflight and multi-instance index consistency: 0.4 |
| Redacted decision logs and bounded core metrics | HTTP request coalescing in generic ASGI middleware |
| Reproducible throughput and p50/p95/p99 benchmarks | New providers, streaming replay, conversations, adaptive thresholds |
| Compatibility notes, examples, CI, and measured release evidence | New embedding runtimes, external backends, negative caching |

These optional integrations are deferred for the initial v0.3.0 release. Basic logs and metrics remain required. Existing `json-v1` responses and OpenAI codecs remain supported; deferring schema caching does not remove existing JSON support.

Support remains **one cache instance coordinating work inside one process**. Two independently constructed cache instances do not share a flight registry, even in the same process. Redis persistence does not extend this guarantee across workers or containers.

## 3. Required invariants

1. Only fully eligible, scoped requests may access shared cached or in-flight results. Missing identity bypasses both mechanisms before candidate access.
2. Singleflight matches **exact requests**, not semantically similar prompts. Semantic matching remains a separately verified cache lookup.
3. One active flight has at most one provider/function execution. A timeout or failed cache write cannot silently elect a replacement while that execution is still active.
4. No global lock is held while running the provider, user hooks, logging handlers, or awaiting another caller.
5. Every joined flight reaches a terminal state on success, error, cancellation, invalidation, or shutdown; waiting callers have a finite timeout.
6. Cancelling one follower does not cancel the leader, shared future, or other followers.
7. Provider exceptions remain provider failures. Cache error policy never swallows them or retries them automatically.
8. Admission, codec, payload-integrity, identity, freshness, and verification rules are not weakened by failure handling or coalescing.
9. Rejected, incomplete, refused, unsupported, or oversized results are not published for shared replay.
10. Explicit invalidation fences older work so it cannot repopulate the cache or publish an obsolete shared response.
11. Cache hits, shared execution, and origin calls are measured separately. Internal rechecks do not inflate request or hit counts.
12. Closing rejects new work and never closes a connection while an admitted cache operation is using it.
13. Caller cancellation is not proof that a worker thread stopped. Such work remains tracked until it exits.
14. Default diagnostics contain neither payloads nor identity values. Digests are not treated as anonymous metric labels.
15. Registries, queues, latency storage, and diagnostic retention have explicit bounds.

## 4. Module design and proposed interface

Use a deep execution module with a small interface. Integration adapters supply an immutable request context, a provider callback, and the existing response codec. They do not implement election, timeouts, retries, failure policy, or independent identity rules.

Paths in the following sections are relative to `LongCache-fork/`. New files and interface names are proposed deliverables.

| Module | Responsibility |
| --- | --- |
| `src/longcache/core/execution.py` — new | Shared prepare/lookup/join/recheck/compute/admit/store/return flow for sync and async callers. |
| `src/longcache/core/singleflight.py` — new | Bounded flight registry, ownership, terminal outcomes, follower attachment/detachment. |
| `src/longcache/core/lifecycle.py` — new | Admission of active work, cancellation tokens, drain, executor ownership, final resource closure. |
| `src/longcache/core/errors.py` — new | Typed operational, capacity, timeout, compatibility, and lifecycle errors. |
| `src/longcache/core/observability.py` — new | Fixed-schema events, counters, histograms, and bounded snapshots; no exporter dependencies. |
| Existing `core/cache.py` | Public methods delegating to these modules; retain policy and scoped maintenance behavior. |
| Existing `core/identity.py` | Sole source of execution identity. Add no persisted identity version unless required by evidence. |
| Existing backends and index | Finite I/O, ownership/cleanup, error translation, and reconciliation after partial failure. |
| Existing integrations | Adapt requests and invoke the shared execution interface; keep unsupported paths as pass-through. |

Keep these implementation modules private. Export only deliberately supported configuration, execution methods, and exception classes. Avoid introducing a general plugin system or arbitrary backend injection.

### 4.1 Public execution methods

Recommended calling forms, to finalize in slice A:

```python
# Proposed v0.3 interface; not available in the inspected v0.2 package.
answer = cache.get_or_compute(
    query,
    lambda: call_provider(query),
    context=context,
    namespace="support",
    ttl=300,
    tags=("support-docs",),
)

answer = await cache.aget_or_compute(
    query,
    lambda: async_call_provider(query),
    context=context,
    namespace="support",
)
```

- Preserve `lookup/alookup`, `get/aget`, `set/aset`, and their v0.2 result types. Separate lookup and store calls cannot promise singleflight because LongCache does not own the intervening computation.
- Both new methods return the documented response type. Sync accepts a synchronous zero-argument callable; async accepts a zero-argument factory producing an awaitable. Reject mismatches before starting execution.
- An operation must be safe to reuse under v0.2 caching rules. Callers must use distinct `context.operation` values for different computations; callable object identity is not a trustworthy substitute.
- Callback arguments and all response-affecting state must already be represented in the request context/query. Retain decorator bypasses for extra arguments and unsupported shapes.
- Admission/verifier hooks must be safe for concurrent invocation and should be deterministic over their supplied inputs. Do not place mutable per-request identity in closure state or serialize arbitrary hooks under a global lock.
- The callback runs at most once for the leader; followers' callbacks are not invoked when a validated result is shared.
- Context, effective TTL, tags, and operational settings are snapshotted for the call. Mutating configuration while requests are active is unsupported.

### 4.2 Proposed settings

Prefer a small set of validated scalar settings over independent behavior flags for every stage:

| Setting | Proposed default | Meaning |
| --- | --- | --- |
| `singleflight_enabled` | `True` | Applies to supported shared-execution methods and their adapters, after eligibility checks. `False` retains independent calls. |
| `singleflight_wait_timeout_seconds` | `30.0` | Maximum follower wait. Does not change the provider's timeout. |
| `singleflight_max_inflight` | `1024` | Maximum active keys per cache instance. |
| `singleflight_max_waiters_per_key` | `256` | Maximum attached followers per key. |
| `cache_error_policy` | `"raise"` | `"raise"` preserves explicit cache exceptions; `"bypass"` permits safe origin execution for recognized runtime cache failures. |
| `backend_timeout_seconds` | `2.0` | Initial SQLite busy/Redis socket/connect timeout. A per-I/O limit, not an end-to-end deadline. |
| `shutdown_timeout_seconds` | `5.0` | Default grace period before reporting incomplete cleanup. |

These defaults are initial design choices, not measured optimal values. Confirm them against expected provider latency and capacity in slice A. Validate positive finite numbers, integer capacities, actual booleans, and policy enums; reject NaN, infinity, bool-as-int, unknown keys, and misspelled environment values.

Initially use a documented internal async cache executor limit of four workers and 64 outstanding submissions, including running work. Reject excess submissions with a typed capacity error; do not queue indefinitely. Re-estimate these defaults from benchmarks before exposing additional tuning settings. Provider coroutines run on their caller's loop, and sync provider callbacks run on their calling thread; neither uses this cache executor.

Bound each retained replay envelope by the existing `max_capture_bytes` and all retained envelopes by an initial 32 MiB per-instance budget. Reserve/release encoded-byte capacity explicitly. If an otherwise valid result exceeds the total budget, mark it non-shareable rather than evicting an unresolved flight or retaining unbounded payloads. Benchmark these limits before finalizing defaults.

Singleflight capacity/timeouts are coordination failures, not dependency outages. `cache_error_policy="bypass"` must not convert them into duplicate provider work. Applications can explicitly disable singleflight if independent execution is preferred.

## 5. Singleflight behavior

### 5.1 Keys and eligibility

Use the existing `RequestContext.exact_key(query, namespace, sharing, embedding, policy)` after the normal scope/shape checks. It includes the exact query and the semantic partition, which already covers scope, operation, provider/deployment, model, instructions, generation options, source versions, codec, embedding generation, and policy.

The internal flight identity additionally includes:

- The cache instance's current invalidation epoch.
- A canonical write-policy digest of effective TTL and sorted/deduplicated tags. Callers requesting different storage behavior must not inherit the first caller's settings accidentally.

These additional fields coordinate transient work; do not modify the persisted v0.2 identity format for them. Do not normalize query text to increase joining, use similarity scores as flight keys, or log full keys.

Missing/unsupported request identity means ordinary pass-through, no cache access, and no flight registration. Runtime embedding/storage outages may use exact scoped coalescing only when a previously validated identity descriptor exists. During cold initialization failure, bypass the cache and registry rather than inventing an incomplete key.

### 5.2 Execution sequence

1. Admit a lifecycle operation and snapshot immutable inputs. Resolve eligibility and complete execution identity.
2. Perform normal lookup. If a verified hit exists, return it. Internal accounting is provisional until the response is accepted for delivery.
3. On a cacheable miss, claim the exact flight under a short registry lock. Join an existing flight or become its leader.
4. Recheck the cache **after joining/claiming**. This closes the lookup/election race. Internal rechecks produce stage measurements, not extra public request counts.
5. A follower that finds a valid cache entry detaches and returns it; otherwise it waits for the flight's terminal outcome within its own remaining timeout.
6. The leader also rechecks, then invokes the provider only if still needed. Provider work and user hooks run outside internal locks.
7. On successful provider return, apply mandatory admission and the configured hook; build a bounded, independent replay envelope using the supported codec.
8. Store if allowed, checking lifecycle token and invalidation epoch under mutation coordination immediately before committing. Complete publication only after the configured write policy is resolved.
9. Publish either the validated replay envelope or an explicit non-shareable/error terminal outcome. Release every waiter and remove the registry entry in `finally`, with identity-safe removal so an old leader cannot delete a newer flight.
10. Followers recheck live cache state after completion. If they use a shared envelope, validate codec/admission and the original scope, policy, and epoch before delivery. Apply the configured verifier to the exact original/current query pair, using a documented exact-match score of 1.0; rejection, abstention, or hook failure never authorizes shared replay. Each gets a fresh decoded object.

Keep one decision/event per external operation. A post-join hit still counts as a hit only if an actual valid cache entry supplied it. A shared live result is separately identified as `source="coalesced"` and does not fabricate a persistent entry hit.

### 5.3 Implementation approach

Use a per-instance thread-safe registry with a `concurrent.futures.Future` or equivalent thread-safe completion object. It supports both threaded sync followers and asynchronous followers without blocking the event loop. Async followers wrap the shared future on their running loop and shield it from caller timeout/cancellation. Never store a loop-bound `asyncio.Future` as the cross-thread registry primitive. See [Python future bridging](https://docs.python.org/3.11/library/asyncio-future.html#asyncio.wrap_future).

The first caller owns the provider execution. Do not add a detached execution scheduler for every leader. Async provider cancellation follows that leader's task; sync functions remain on their calling thread. This is a deliberate initial contract with a small interface.

Async waiters must not occupy executor threads while waiting. Keep strong references to any owned tasks and release per-loop bridges after completion/cancellation. A closing loop must not leave an unresolved shared record or trigger unobserved-exception warnings.

Prohibit blocking sync shared-execution/close calls from an active event-loop thread; direct callers to the async methods. This avoids waiting synchronously on work that needs the same loop. Detect recursive execution of the same active key by its owner and raise `SingleflightReentrancyError` rather than self-waiting.

### 5.4 Failure and cancellation contract

| Situation | Required behavior |
| --- | --- |
| 20 overlapping supported identical calls; admissible result | One origin execution; every caller gets an equivalent supported response. |
| Different scope/context/query/write policy | Different flight; no result sharing across identities. |
| Follower timeout | Raise `SingleflightTimeoutError` for that follower; detach it; leader and other followers continue. No automatic replacement execution. |
| Async follower cancellation | Propagate its `CancelledError`; do not cancel the shared future or leader. |
| Leader provider exception | Leader receives original provider exception. Followers receive a fresh `SingleflightLeaderError` chained to it; no negative cache entry and no hidden retry. |
| Async leader cancellation | Leader receives `CancelledError`; followers receive a leader-cancelled terminal error. A later explicit call may start a new flight after cleanup. |
| Sync caller stops waiting externally | Its thread is not forcibly terminated. Track execution until it actually finishes. |
| Admission rejects result, including refusal | Leader receives its own origin result if that is normal provider behavior. Do not share it. Followers detach and run their own callbacks once without rejoining that completed wave. |
| Result exceeds replay bound | Same non-shareable handling; record a bounded reason. Never hold unbounded response copies. |
| Follower admission/verifier rejects, abstains, or throws | Do not return the shared response; execute that caller's origin callback independently once, under normal admission/no-store rules. |
| Flight/waiter capacity reached | Raise `SingleflightCapacityError`; existing flights are unaffected. |
| Cache store fails after admitted result | Apply section 6. In bypass mode a validated transient envelope may serve attached followers; this is not a stored cache hit. |
| All followers leave | Leader continues for its own caller. No extra detached origin execution is created. |
| Leader exits unexpectedly | `finally` publishes an abort outcome and releases waiters. Do not swallow `BaseException` from the leader. |
| Later explicit retry after terminal failure | A new flight is allowed; LongCache supplies no provider retry/backoff policy in v0.3. |

Non-shareable results are an explicit exception to the one-origin-call success guarantee. Do not turn rejected responses into implicitly shareable results merely to reduce calls. Document this behavior and measure it separately.

The follower timeout is not a provider deadline. Require finite provider timeouts in documented examples; arbitrary user code cannot be forcibly stopped safely. Python cancellation and shielding behavior are documented in [asyncio tasks](https://docs.python.org/3.11/library/asyncio-task.html#shielding-from-cancellation).

### 5.5 Invalidation during active work

Introduce one monotonic invalidation epoch per cache instance. Advance it under mutation coordination when explicit scoped/tag invalidation or clear begins, even if no persisted entry currently exists. This conservative global fence prevents an old miss from repopulating data that an operator just invalidated; partition-specific epochs can be a later optimization.

- Include the captured epoch in flight identity and commit/publication checks.
- When an explicit invalidation advances it, older leaders may return their own origin result to their original caller, but cannot store or share it afterward.
- Existing followers receive `SingleflightInvalidatedError` unless they already committed delivery before invalidation. There is no automatic provider retry.
- A later explicit request uses the new epoch. New and old executions may overlap across this intentional invalidation transition; the guarantee is per flight/epoch.
- Linearize successful replay/commit under the mutation coordination. Never promise to retract a result already handed to application code.
- Failed invalidation raises an error and marks the affected cache state unavailable; never report successful invalidation while serving uncertain old state.
- TTL expiry and capacity eviction still use final live-entry checks. They are not source-version changes and need not advance the explicit invalidation epoch.

This fences in-process writes and shared results. Applications must still provide accurate corpus/document versions for external source changes, and other processes remain outside the guarantee.

## 6. Explicit cache failure policy

### 6.1 Defaults and terminology

Keep `cache_error_policy="raise"` as the default to preserve explicit v0.2 failure behavior. Document `"bypass"` for applications that prefer availability during recognized cache outages.

Bypass means **call the origin without trusting the failed cache path**. It never means serving a failed, stale, undecodable, or unverified candidate. A cache hit requires all existing v0.2 checks in either mode.

| Failure | `"raise"` | `"bypass"` |
| --- | --- | --- |
| Recognized embedding runtime outage | Raise typed cache error before origin work | Skip cache reuse/write for this operation; call origin. |
| Index search/retrieval operational failure | Raise typed cache error | Skip cache reuse; call origin. Suppress writes if coherence is uncertain. |
| Storage outage during lookup | Raise typed cache error | Call origin; no fallback to an unverified stale candidate. |
| Store/index update failure after origin succeeds | Raise typed cache error documenting that origin execution already occurred | Return successful origin result, emit write-failure event, share only validated transient replay if allowed. |
| Optional persistent hit-count update fails after final validation | Do not fail an otherwise valid response; report accounting failure in either mode | Same; in-process counters remain accurate. |
| Candidate codec/integrity invalid | Reject candidate and continue verified search or miss, following v0.2 policy | Same; never serve the invalid candidate. |
| Admission/verifier rejects, abstains, or hook fails | Preserve conservative no-store/no-hit policy | Same; cache policy cannot authorize rejected output. |
| Bad config, incompatible manifest/model generation, invalid vector contract | Fail explicitly | Fail explicitly; do not hide deterministic compatibility defects as an outage. |
| Provider/function error or cancellation | Propagate according to section 5 | Same; no cache fallback or automatic retry. |
| Clear/invalidate/maintenance failure | Raise; do not claim success | Raise; bypass policy does not turn failed maintenance into success. |
| Closed cache, flight capacity/timeout | Raise the relevant lifecycle/coordination error | Same; do not start duplicate work as a hidden fallback. |
| Logging/measurement failure | Isolate from valid request behavior | Same. |

Translate known failures at the owning module, retaining a bounded stage/reason. Do not blanket-catch all `Exception` around the entire request and call the provider again; that can duplicate an origin execution after a store failure and conceal programming errors. `MemoryError`, `KeyboardInterrupt`, `SystemExit`, and unknown defects are not ordinary bypass conditions.

### 6.2 Partial mutation and recovery

The existing store → index-add → rollback sequence needs explicit reconciliation when rollback also fails or a remote write's outcome is uncertain:

1. Mark cache coherence uncertain under mutation coordination; stop new cache reads and writes against that state.
2. Finish the current operation according to the selected policy without serving an uncertain candidate.
3. Keep the origin result and store failure separate. Never repeat the provider because persistence failed.
4. Retain only bounded recovery state. Report health as `degraded` with a fixed reason code, not raw exception text.
5. In the initial implementation, require `close()` and a new instance to recover uncertain index/store state. Startup validates the manifest and rebuilds from live, compatible entries. Do not add a circuit breaker or automatic repair framework to v0.3.
6. Transient lookup failures without partial mutation can be retried by the next request under the same policy. Background sweep failures use their own bounded retry schedule.

Use finite SQLite busy timeouts and Redis connect/socket deadlines. A socket timeout is not an end-to-end bound for a multi-command operation; check operation deadlines between steps. Keep Redis automatic write retries disabled unless their idempotency is separately proven. Fault tests must cover timeouts after a potentially committed write.

For ASGI, cache errors before response start follow the selected policy. Once upstream headers/body have been forwarded, an incidental cache-write failure cannot replace that response or start the app again. Record it, apply coherence safeguards, and preserve the already-started response. Document this unavoidable transport limit on strict behavior.

## 7. Lifecycle and resource ownership

### 7.1 States and operation tracking

Use `OPEN → CLOSING → CLOSED` with explicit active-operation tokens. Track cache worker operations separately from provider callbacks and waiting followers.

- `OPEN`: accept calls; create/register active work before touching resources.
- `CLOSING`: reject new calls, stop sweeper scheduling, and allow admitted operations a bounded grace period. Only their valid operation tokens may continue cache access.
- At grace expiry, revoke remaining cache-publication permissions and wake waiting followers with a shutdown outcome. Do not permit late writes.
- `CLOSED`: owned resources are released and no cache work can use them. A detached user/provider function can still be running, but it cannot access the closed cache through its revoked token.

If an actual cache worker still owns a connection at the deadline, remain `CLOSING` and raise `CacheShutdownTimeoutError` with redacted pending counts. Final cleanup runs exactly once when the last owner exits. Do not set `CLOSED` and claim all resources are freed while a worker is still using them.

Repeated and concurrent close calls join the same cleanup; they do not double-close resources. `close()`/`aclose()` from inside an active provider/hook on the same cache must be rejected as reentrant lifecycle use rather than waiting on itself.

### 7.2 Sync and async cleanup

Add `aclose(timeout=None)`, `__aenter__`, and `__aexit__`; retain sync context managers. `close(timeout=None)` uses the configured default when no override is supplied.

Cleanup order:

1. Atomically enter `CLOSING` and stop accepting external work.
2. Stop/wake the sweeper; prohibit new background submissions.
3. Drain admitted work within the grace deadline without holding registry/mutation/backend locks.
4. On deadline, revoke tokens, terminate follower waits, and cancel owned async leaders cooperatively on their owning loop. Never manipulate another loop's task directly.
5. Cancel queued cache jobs; retain references to already-running jobs until they exit. Their cooperative cancellation checks prevent late mutations/accounting.
6. Once backend users are gone, close owned connections/Redis pool and release the executor. Mark `CLOSED` only after completion.

Async cleanup must not block the event loop. If its caller is cancelled, preserve a strongly referenced cleanup task so cleanup continues; propagate caller cancellation normally. A subsequent `aclose()` can join that same cleanup. Do not swallow cancellation or treat it as a successful resource drain.

When a context manager is already unwinding a provider/application exception, preserve that original exception as the primary failure. Report any additional cleanup failure with a bounded diagnostic and chaining where appropriate; never silently replace the original failure or suppress it.

Never close caller-supplied OpenAI clients, shared injected embedders, or a supplied `LongCache` instance implicitly. Adapters close only resources they created; add explicit ownership flags and close/context-manager forwarding where needed. Middleware ownership is wired through the application's explicit lifespan, without changing unrelated application's lifespan behavior.

### 7.3 SQLite and workers

Recommended initial fix: replace thread-local SQLite connections with one backend-owned connection, opened with `check_same_thread=False`, guarded by the backend's existing `RLock` for **every** connection/cursor/transaction operation. Close it only after admitted users drain. Keep cursors internal and retain transactional schema/manifest behavior.

This simplifies complete cleanup and avoids accumulating one connection per executor thread. It is not permission for simultaneous unguarded connection use. Python's [SQLite connection guidance](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.connect) requires user serialization where applicable. Reject builds with `sqlite3.threadsafety == 0` for this cross-thread path. Verify file-backed and `:memory:` behavior, rollback, and WAL configuration.

Preserve lock order: lifecycle admission is short; no lifecycle/flight lock spans backend work. When simultaneous locks are needed, retain mutation → index → backend order. Embedding and user hooks run outside those locks. Emit logs only after locks are released. Document permitted order next to the relevant private methods.

Replace untracked `to_thread` submissions with tracked, bounded cache-worker submissions. Cancelling the async awaiter sets a token and cancels queued work when possible, but does not falsely mark a running thread finished. Python's [executor shutdown contract](https://docs.python.org/3.11/library/concurrent.futures.html#concurrent.futures.Executor.shutdown) does not terminate already-running functions.

### 7.4 Sweeper

- Preserve existing cleanup semantics and index rebuild behavior; do not move scale-oriented rebuild redesign into this release.
- Catch recognized backend/index operational failures; emit a redacted event and health metric.
- Use a stop-event-based retry interval of 1, 2, 4, up to 60 seconds after transient failures; no tight loop and no writes against uncertain coherence.
- An unknown programming failure marks the background task failed and reports health; do not conceal it in endless retries.
- `close()` wakes the wait immediately. A bounded backend operation must finish before its resources close.

## 8. Integration support and migration

| Entry point | v0.3 requirement |
| --- | --- |
| Manual `lookup/get/set` and async forms | Existing semantics plus explicit operational failures, lifecycle tracking, and decision metrics. No promise to coalesce separately managed origin calls. |
| New `get_or_compute/aget_or_compute` | Complete singleflight contract and primary public test surface. |
| Query-only sync/async `@cache.cached` | Delegate to shared execution, retain qualified-function operation identity and extra-argument bypasses. |
| `CachedOpenAI` sync/async supported subset | Delegate to shared execution, retaining exact model/instruction/settings/codec rules and caller client ownership. |
| Supported ASGI JSON route | Preserve scoped caching, capture bounds, auth resolution, disconnect behavior, and headers; add failure/lifecycle/metrics behavior. |
| Generic ASGI request coalescing | Deferred. Identical body text does not prove equivalent request middleware side effects, headers, or disconnect semantics. Do not share an arbitrary downstream app invocation. |
| LangChain/LangGraph/LlamaIndex opaque wrappers | Retain documented compatibility pass-through. Do not newly advertise cache capability. |
| Streaming/tool/multimodal/multi-turn paths | Retain bypass behavior and stable reasons. |
| Standalone async Redis | Remains experimental; no new end-to-end `LongCache` claim. |

The core 20-request gate applies to the documented shared-execution methods, query-only decorators, and supported OpenAI calls in sync and async modes. The release support matrix must name these entry points explicitly.

Migration notes must explain:

- Identical concurrent calls may now return the same generated completion rather than independently sampled completions. This is appropriate only for operations already accepted as reusable. `singleflight_enabled=False` preserves independent execution.
- Cache exception default remains strict. Bypass is an explicit application choice; strict write failure can occur after the provider has already run, so blind application retries may incur another call.
- Follower timeout, capacity errors, leader cancellation, and reentrancy errors are new documented outcomes.
- Format-2 cache entries, identity, Python 3.11/3.12 support, and existing codec contracts remain unchanged unless a separately justified compatibility finding requires a revised plan.
- Async cache methods still use bounded worker execution over synchronous supported backends; they do not imply async Redis support.
- Existing cost-savings fields remain unmeasured unless actual usage is available. Follower copies of provider usage must not be summed as separate provider calls.

## 9. Decision logs and core metrics

### 9.1 Events and privacy

Use standard Python logging under a documented `longcache` logger with a `NullHandler`. Do not configure global logging, add handlers automatically, or require a metrics library.

An allowlisted completion event contains:

```json
{
  "event": "longcache.execution",
  "event_version": 1,
  "mode": "async",
  "entry_point": "openai",
  "outcome": "miss",
  "source": "coalesced",
  "reason": "accepted_shared_result",
  "flight_role": "follower",
  "backend": "sqlite",
  "duration_ms": 42.1
}
```

Do not include query text, responses, instructions, credentials, headers, URLs, tenant/user values, arbitrary namespace/operation/model strings, full identity/flight digests, or exception messages. Provider exception text may itself contain private content. Do not use `exc_info=True` on default events.

Use a fixed, documented reason-code allowlist. Application hook reasons collapse to `application_policy` for metric labels; bounded syntax alone does not prevent infinitely many different values. Logs may include the bounded supplied code only under an explicit diagnostic opt-in.

Normal decision events are DEBUG-level opt-in. Cache dependency/coherence/shutdown failures use rate-limited WARNING events with bounded limiter storage. Failure in diagnostic emission is contained and does not trigger recursive logging or change decisions. Slow/blocking application logging handlers remain application-owned; show a queue-handler configuration example and exclude them from core latency claims.

### 9.2 Metric definitions

Store process-local counters and fixed-bucket histograms with a short dedicated lock. Do not retain raw timing samples. Expose a redacted in-memory `metrics(operator=True)` snapshot that does not call the backend and remains available during degraded state and after close.

| Metric family | Definition |
| --- | --- |
| Requests | One terminal outcome per external cache operation; execution and direct lookup/store are distinct operation types. |
| Lookup decisions | Hit, miss, bypass counts for external lookups or the final execution decision; internal rechecks are excluded. |
| Verification | Accept/reject/abstain/failure counts, including attempts before a later accepted candidate. |
| Admission | Accepted/rejected/failed writes or shared envelopes; distinguish storage from replay checks. |
| Errors | Stage and fixed failure reason; provider errors separate from cache errors. |
| Singleflight | Leaders, joined followers, successful shared deliveries, non-shareable results, timeouts, cancellations, capacity rejections. |
| Origin executions | Actual callback/provider invocations, including independent calls after a non-shareable result. |
| Latency | End-to-end cache execution plus prepare, embedding, lookup, verification, wait, origin, admission, and store stages. |
| Resource/health gauges | Active flights/followers/cache jobs, queue depth, open owned connections, lifecycle and coherence state. |
| Observability drops | Suppressed/rate-limited events and accounting failures; no recursive events. |

Allow labels only from bounded sets such as operation type, supported entry point, mode, outcome, source, stage, backend kind, reason, and flight role. Do not take their Cartesian product on every metric: each family declares only necessary dimensions and a maximum series count. Initial budget: at most 2,000 populated internal series per instance, enforced by allowlists and tested under adversarial inputs.

Suggested latency buckets in seconds: `0.0001, 0.0005, 0.001, 0.005, 0.01, 0.05, 0.1, 0.5, 1, 5, 30, 120, +Inf`. Use a monotonic clock. Benchmarks retain separate sample arrays offline to calculate exact percentiles; histogram snapshots are not exact p99 measurements.

### 9.3 Accounting rules

- A delivered validated persisted hit increments entry hits once. Inspection, rejected candidates, cancellation before delivery, and internal rechecks do not.
- Origin callback count is measured at actual invocation. A flight with 19 followers is not 20 provider calls.
- A shared transient response is `source="coalesced"`, not a persisted hit. A follower that rechecks and serves a valid entry is a cache hit and also has follower role; these are different dimensions.
- A cache hit rate is accepted cache hits divided by eligible external lookup/execution decisions, with bypass/error/cancelled counts published separately. Preserve legacy `stats()` field definitions and document any newly added metric's denominator rather than silently changing old fields.
- Stage errors can accompany a successful origin response under bypass policy. Record the successful request and error event without marking two terminal request outcomes.
- Never claim measured money saved from a count alone. Provider token/cost measurement is outside this scope; existing estimate fields stay zero or explicitly unavailable.

Keep `track_stats=False` as a genuine measurement opt-out for nonessential counters/histograms; lifecycle tracking still operates. Retain final snapshots after closure without fetching backend data.

The existing `_partition_stats` dictionary is unbounded. Replace it with bounded retention (initially 1,024 partition records) or an equally bounded implementation. If old per-partition statistics are evicted, expose a reset/window marker and document that scoped statistics cover the retained window. Never silently claim lifetime exactness after eviction. Aggregate process counters must remain exact independently of this retention.

## 10. Acceptance and failure-injection tests

Use events, barriers, explicit task registration, fake monotonic clocks for deadline logic, and per-test watchdogs. Do not prove concurrency with arbitrary sleeps. Ensure the leader is held until the expected followers are attached, then release it. Run potentially hanging thread/shutdown cases in a subprocess so a failed test cannot hang CI indefinitely.

| Scenario | Required result |
| --- | --- |
| 20 identical cold sync calls | One origin execution, one successful store, 20 equivalent responses, no remaining flights. |
| 20 identical cold async calls | Same guarantee; event loop remains responsive and no follower consumes an executor thread to wait. |
| Warm hit | Zero origin executions; single correct entry-hit increment per delivered result. |
| Lookup/claim race | Cache populated before join is found by post-join recheck; no duplicate origin call. |
| Scope/context mutation matrix | Every v0.2 partition field remains isolated; exact-query changes do not coalesce. |
| Different TTL/tags | Defined separate flights/write behavior; no accidental first-writer policy inheritance. |
| Missing identity/unsupported shape | No registry access, embedding, cache read, or cache write; ordinary pass-through. |
| Different keys running together | Providers overlap; no registry/global lock serializes unrelated work. |
| Sync thread plus async caller sharing one instance | One flight when the operation identity is equal; no cross-loop future misuse. |
| Multiple event loops on separate threads | Shared-future completion works; closing one follower loop does not cancel other waiters. |
| Cancel one follower | Others succeed; no duplicate execution and waiter count returns to zero. |
| Timeout one/all followers | Timed-out callers detach; leader continues; no election of a second leader. |
| Cancel async leader | All followers terminate with the documented error; no partial storage; later explicit retry works. |
| Provider throws | One failing origin per flight; typed follower errors; no automatic retry or cached failure. |
| Recursive same-key callback | Immediate typed reentrancy error instead of self-deadlock. |
| Refusal/invalid/oversized result | No shared replay or store; original response behavior preserved; followers use the documented independent path. |
| Mutable dictionary/SDK response | Changing one caller's result does not alter another caller's response or persisted payload. |
| Follower policy refuses exact replay | No shared response is delivered; that follower follows the documented independent-origin path. |
| Store/index/rollback failure | No silent duplicate origin call; strict/bypass outcomes and degraded-state behavior match the table. |
| Remote timeout after possible commit | No unsafe replay; new instance rebuilds only valid compatible entries. |
| Invalidate/clear during provider execution | Old flight cannot write or publish afterward; empty-store invalidation also fences it. |
| Deletion/expiry during verification/recheck | No expired or deleted entry delivered; preserve v0.2 final validation tests. |
| Close during active hit/miss/store/provider | Defined drain or timeout; no resource closed while in use and no late publication. |
| Repeated/concurrent close and cancelled aclose | Cleanup is owned once, caller cancellation propagates, subsequent close can join. |
| SQLite worker/sweeper connections | All owned connections close; no thread-affinity exceptions; no worker can reopen after close. |
| Redis unavailable/connect/read timeout | Bounded I/O and correct policy; no busy retry or accidental use of a shared test database. |
| Sweeper transient/unknown failure | Bounded retry or visible failed health as specified; close wakes its wait promptly. |
| Flight/waiter/executor/replay-byte/metrics/partition caps | Bounded memory and defined overflow behavior; existing work completes and counters reconcile. |
| Telemetry disabled/broken handler | Same cache decisions and response results; no raw data or recursive error logging. |
| Logging/metrics adversarial identities/reasons | No secret leakage or unbounded label/retention growth. |
| OpenAI/decorators sync/async | Same core guarantees and response types through supported codecs. |
| ASGI | Existing auth/body/header/disconnect/privacy behavior preserved; no promised HTTP coalescing. |
| Restart and rollback | v0.2 format-2 stores remain readable by both versions under unchanged identity/codec settings. |

Run applicable scenarios across memory, file-backed SQLite, and a real Redis service, with flat and HNSW indexes. At minimum, run the 20-request gate across all six backend/index combinations for both modes. Integration-specific cases use supported SDK objects and provider stubs, without live API cost.

Separate deterministic reliability tests from real-model safety/performance evaluation. Reuse the v0.2 frozen safety dataset and changing-document RAG checks; do not replace them with synthetic identical-request success counts.

## 11. Benchmark protocol and initial budgets

### 11.1 Workloads

Add `evaluation/reliability.py`, `evaluation/configs/v0_3_reliability.json`, and JSON/Markdown report output. The manifest records baseline/candidate source hashes, lock hash, dataset/model revisions, thresholds, cache sizes, backend/index settings, interpreter, hardware, OS, worker/thread limits, concurrency, warmup, seed, sample counts, timeout/cancellation rates, and observability mode.

Required workloads:

1. Warm exact and safe-paraphrase hits at 1K and 10K entries.
2. Distinct misses at concurrency 1, 20, and 100 with a deterministic 100 ms provider stub.
3. Cold identical bursts of 20 callers, and separate overload bursts that exceed configured caps.
4. Mixed traffic with held-out identities/contexts and fixed hit/miss proportions.
5. Failure workloads: dependency timeout, rejected admission, provider failure, cancellation, and invalidation during a burst.
6. Repeated construction/use/close cycles and sustained distinct-key operation for resource retention.

Measure cache orchestration with a deterministic embedder and end-to-end execution with the pinned real model in separate reports. Use one configured Torch/FAISS thread for a controlled baseline and report an additional application setting if useful. Record provider stub delay separately; never attribute its 100 ms to cache overhead.

Run baseline v0.2 and candidate in isolated workers with matched dependencies/hardware, alternating run order to reduce drift, following the existing paired benchmark lesson. Do not compare a warm candidate against a cold baseline. Avoid concurrent benchmark jobs on the measurement host.

Report throughput, p50/p95/p99, errors/timeouts, number of actual origin calls, coalesced deliveries, queue wait, CPU, peak/stable RSS, active threads, and owned connection counts. Include offered-load or scheduled-arrival measurements in addition to closed-loop throughput so queueing is not hidden by slow clients. Failed/time-out requests remain in the report.

Use at least five measured repeats after warmup and at least 10,000 successful observations per principal latency cell before treating p99 as release evidence. Publish full counts and per-repeat percentiles; do not infer p99 from 20-request bursts or average percentiles into a single unexplained value.

### 11.2 Proposed release budgets

Freeze these initial targets after slice A, before tuning. They are proposed targets, not claims about current performance.

| Gate | Initial acceptance target |
| --- | --- |
| Cold identical burst | Exactly one origin call and 20 successful equivalent results in every supported required cell. |
| Terminal-state correctness | Zero stranded followers, duplicate owners, unsafe hits, or late writes in the deterministic failure suite. |
| Safety | Existing v0.2 isolation/admission/quality gates still pass with useful-hit coverage; no regression hidden by bypassing more traffic. |
| Warm-hit latency | Candidate p95 <= `1.15 × matched v0.2 p95 + 1 ms`; p99 <= `1.20 × matched v0.2 p99 + 2 ms`. |
| Singleflight overhead | With deterministic embedding and the 100 ms stub, p95 added orchestration <= 5 ms at concurrency 20 on the frozen host. |
| Distinct-miss throughput | At least 90% of matched v0.2 throughput on the same bounded workload, while errors and completion counts are equivalent. |
| Core measurement overhead | Tracking enabled versus disabled adds at most `5% of disabled p95 + 0.5 ms`; DEBUG handlers disabled in this gate. Report logging enabled separately. |
| Bounded state | Registry, waiter, executor, series, and retention limits are enforced and return to expected idle levels. |
| Cleanup | Normally completing workloads drain inside the configured grace period; intentionally stuck work produces an explicit timeout without unsafe closure. |
| Resource regression | No accumulating owned threads/connections/flight records over at least 100 create/use/close cycles; report RSS trends without treating allocator retention alone as a leak. |
| Privacy | Zero forbidden payload/identifier/exception-text values in default event, metric, and header checks. |

Performance targets apply on a declared dedicated reference host, not as universal CI-runner timing promises. Standard hosted CI runs deterministic correctness tests; a controlled performance job supplies release evidence. Keep failed runs as diagnostics. A budget change requires a written design/workload rationale and a new manifest version, not a silent relaxation after seeing candidate results.

## 14. Completion and release decision

The implementation is complete only when:

- [ ] Every required roadmap item maps to code, behavior tests, documentation, and a recorded result.
- [ ] Required sync/async entry points pass the 20-identical-request gate across the supported backend/index matrix.
- [ ] Scope, exact query, operation, codec, write policy, and invalidation epoch control flight joining consistently.
- [ ] Follower timeout/cancellation, leader error/cancellation, overload, invalidation, and shutdown terminate under the documented contract.
- [ ] Recognized cache outages follow strict/bypass settings without unsafe candidates or duplicate origin calls after write failure.
- [ ] SQLite/Redis/worker/sweeper ownership is verified; timeout reports distinguish incomplete cleanup from successful closure.
- [ ] Logs, metrics, and retained diagnostics are bounded, redacted, and correctly distinguish cache reuse from shared origin execution.
- [ ] Existing v0.2 safety, freshness, persistence, and supported response-type checks continue to pass.
- [ ] Frozen latency, throughput, overhead, and resource targets pass with raw counts and reference-host details.
- [ ] Clean-wheel, supported Python, SDK, documented-example, migration, and rollback checks pass.

- [ ] Release notes state single-instance/process limits, deferred optional features, new failure outcomes, and known cancellation limits.
