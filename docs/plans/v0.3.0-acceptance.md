## Release gates still requiring external or controlled evidence

1. Run hosted CI after the user's manual push.
2. Run the full-count reliability protocol on a predeclared controlled host, including
   real-model timing where claimed. Local quick/smoke results are not substitutes for
   full miss/burst/overload and the proposed singleflight-overhead gate.
3. Complete inherited domain-representative dataset review and an explicit release
   candidate feedback window before deciding to publish.
4. Verify the exact built artifacts, version metadata, compatibility/rollback, and
   supported matrix. Tagging and publication remain separate user-controlled actions.

Prometheus, OpenTelemetry, schema/Pydantic replay, distributed coordination, and HTTP
app invocation coalescing are deferred and are not included-feature release gates.

| Release-candidate feedback | Pending | Complete the documented feedback window and revalidate material fixes |

Pushing the development branch is allowed before these gates are complete. A push
enables CI; it is not evidence that CI passed or that v0.3.0 is ready to publish.
Full benchmark preparation/commands are in [benchmarks](../benchmarks.md). The plan
proposes at least five working days for candidate feedback; record the actual window
and its outcome before the final release decision.
